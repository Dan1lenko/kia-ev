# KIA EV Project — Coding Rules

## 1. Server vs Client Components

- **За замовчуванням усі компоненти — Server Components.** Не додавай `"use client"`, якщо це не потрібно.
- `page.tsx` та `layout.tsx` **завжди мають бути серверними компонентами**. Не роби їх клієнтськими цілком.
- Якщо на сторінці потрібна інтерактивність (стан, ефекти, обробники подій, хуки типу `useState`, `useEffect`, `onClick` тощо) — винось цю логіку в **окремий маленький клієнтський компонент**, а `page.tsx` імпортує і рендерить його.
- `"use client"` пишеться максимально "глибоко" в дереві компонентів — тільки там, де дійсно потрібна інтерактивність, а не на весь блок сторінки.
- Дані (fetch, робота з БД, ENV-секрети) отримуються **на сервері** (в Server Component або Server Action), а не в клієнтських компонентах.

## 2. Перевикористання компонентів

- Один компонент — одна відповідальність (Single Responsibility).
- Якщо однаковий UI-блок повторюється на 2+ сторінках — виносити в `components/ui` або `components/shared`, а не дублювати код.
- Компоненти, специфічні лише для однієї сторінки/роуту, зберігати локально в `_components` цього роуту, а не в глобальній папці `components`.
- Пропси компонентів типізувати через `interface` або `type`, не використовувати `any`.
- Уникати "надутих" (god) компонентів — якщо файл компонента більше ~150-200 рядків, варто розбити на менші.

## 3. Іменування файлів

- Компоненти — `PascalCase.tsx` (наприклад, `ProductCard.tsx`).
- Утиліти, хуки, конфіги — `camelCase.ts` (наприклад, `formatPrice.ts`, `useCart.ts`).
- Спеціальні файли Next.js — лише зарезервовані назви: `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx`, `route.ts`, `template.tsx`.
- Кастомні хуки завжди починаються з `use` (`useAuth.ts`) і завжди клієнтські (`"use client"` не ставиться в самому хуку, а в компоненті, що його використовує, якщо хук викликається на клієнті).

## 4. Дані та запити

- Fetch-запити виконувати в Server Components максимально близько до місця використання даних (Next.js кешує дублікати fetch автоматично).
- Мутації (створення/зміна/видалення даних) робити через **Server Actions** (`"use server"`), а не через клієнтські API-виклики, де це можливо.
- Не передавати секретні ключі/токени в клієнтські компоненти.

## 5. Метадані та SEO

- Кожен `page.tsx` повинен експортувати `metadata` (або `generateMetadata` для динамічних сторінок).
- Спільні метадані (title template, opengraph за замовчуванням) виносити в кореневий `layout.tsx`.

## 6. Стилізація

- Використовувати **TailwindCSS v4** як єдину систему стилів. Не змішувати підходи.
- Шрифт проекту: **Poppins** (Google Fonts).
- Спільні дизайн-токени (кольори, відступи, шрифти) виносити в Tailwind конфіг або CSS-змінні, а не хардкодити значення по всьому коду.

## 7. Помилки та завантаження

- Для кожного сегмента роуту, де можливе тривале завантаження — додавати `loading.tsx`.
- Для сегментів, де можлива помилка виконання — додавати `error.tsx` (обов'язково клієнтський компонент).
- Для неіснуючих сторінок — `not-found.tsx`.

## 8. Загальні принципи

- DRY (Don't Repeat Yourself) — дублювання коду/розмітки виносити в перевикористовувані компоненти чи хелпери.
- Уникати зайвої вкладеності папок — не створювати підпапку заради одного файлу.
- Логіку (обчислення, форматування, валідацію) виносити з JSX-компонентів у `lib/` або `utils/`.
- Типи, що використовуються в кількох місцях, виносити в `types/`, а не дублювати `interface` в кожному файлі.
